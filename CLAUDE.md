# CLAUDE.md

## Rules

- **Python env**: Always use `.venv/bin/python` (not system `python3`).
- **Commits**: No `Co-Authored-By` lines. Single-line messages (no body).
- **Dependencies**: Managed in `requirements/*.txt` (used by local dev and Docker).
- **Docs sync**: When modifying code, update CLAUDE.md and ARCHITECTURE.md to reflect changes.
- **No memory**: Never use the auto-memory system (no MEMORY.md, no memory files). All persistent context belongs in CLAUDE.md or ARCHITECTURE.md.
- **Error handling**: App should crash on unexpected errors. `try/except` only for expected, recoverable errors. Custom exceptions in `exceptions.py`.
- **No API backward compat**: Project has no external users yet — don't preserve old Python APIs, function signatures, or import paths. Rename, delete, and rewrite freely; no shims or re-export modules. DB schema changes still go through Django migrations as normal — existing installs must upgrade cleanly.

## Project Overview

OpenOutreach — self-hosted LinkedIn automation for B2B lead generation. Playwright + stealth for browser automation, LinkedIn Voyager API for profile data, Django + Django Admin for CRM (models owned by this project).

## Commands

```bash
# Docker
make build / make up / make stop / make logs / make up-view

# Local dev
make setup    # install deps + browsers + migrate + bootstrap CRM
make run      # run daemon
make admin    # Django Admin at localhost:8000/admin/

# Testing
make test / make docker-test
pytest tests/api/test_voyager.py   # single file
pytest -k test_name                # single test
```

## Architecture (quick reference)

For detailed module docs, see `ARCHITECTURE.md`.

- **Entry**: `manage.py` — stock Django management. `rundaemon` command (migrate → onboard → validate → task queue loop). `manage.py` with no args defaults to `rundaemon`. Onboarding logic in `onboarding.py`: `OnboardConfig` (pure dataclass), `missing_keys()`, `collect_from_wizard()`, single `apply()` write path. Docker `start` script handles Xvfb/VNC, then `exec python manage.py rundaemon`.
- **State machine**: `enums.py:ProfileState` — QUALIFIED → READY_TO_CONNECT → PENDING → CONNECTED → COMPLETED / FAILED. `Deal.connected_at` (crm 0014) stamps the first PENDING→CONNECTED transition (set in `linkedin/db/deals.py:set_profile_state`) — feeds the dashboard "invitations acceptées/jour" chart. Deal.state is a CharField with ProfileState choices (no Stage model). `Outcome` (converted/not_interested/wrong_fit/no_budget/has_solution/bad_timing/unresponsive/unknown) on Deal.outcome. `Lead.disqualified=True` = permanent exclusion. LLM rejections = FAILED Deals with wrong_fit outcome (campaign-scoped).
- **Task queue**: `Task` model (persistent). Three types: `connect`, `check_pending`, `follow_up`. Handlers in `linkedin/tasks/`, signature: `handle_*(task, session, qualifiers)`. Task creation is centralized in `linkedin/tasks/scheduler.py` — no other module inserts Task rows. `set_profile_state()` fires `on_deal_state_entered(deal)`, which enqueues the task implied by the new state (CONNECTED → follow_up, PENDING → check_pending). The daemon calls `reconcile(session)` whenever the queue has no ready task: it recovers stale RUNNING rows, seeds one connect per campaign, and re-creates tasks for any active Deal without a pending task. This is the retry mechanism — a crashed handler leaves a FAILED task with no successor, and the next idle cycle re-creates it. On 401 (`AuthenticationError`), the daemon calls `session.reauthenticate()` and marks the task FAILED; reconcile picks it up.
- **ML pipeline**: GPR (sklearn) + BALD active learning + LLM qualification. Per-campaign models stored in `Campaign.model_blob` (DB). **EKOALU lead routing** (`ekoalu/lead_routing/`, patches `create_enriched_lead` + `get_leads_for_qualification` via `apps.py`): each Lead is attributed to the campaign that discovered it (`LeadDiscovery` model), and a campaign only qualifies *its own* discovered leads instead of the whole base — kills the cross-campaign over-qualification (~97% wrong_fit by construction). Kill-switch `EKOALU_SCOPED_QUALIFICATION=0` or sentinel `data/scoped_qualification_disabled.flag`. Backfill in-flight leads with `manage.py backfill_lead_sources`. Per-campaign targeting criteria (geo + role rules) live in `Campaign.campaign_objective`, applied from the ops Excel via `manage.py apply_campaign_criteria`. **Google sourcing** (`ekoalu/google_sourcing/`, command `manage.py source_via_google`): finds LinkedIn profile URLs via Google search results (`site:linkedin.com/in "Company" "role"`) instead of LinkedIn's own search, creates URL-only leads + `LeadDiscovery` (the daemon enriches/qualifies them later in its own browser session — no second browser). Backend: **Serper.dev** (Google Custom Search JSON API is closed to new customers since 2026). Config: env `SERPER_API_KEY` (1 credit/query, 2,500 free trial credits). ABM-first. **Source routing (12/06)**: ABM campaigns are sourced via Serper ONLY — `ekoalu/google_sourcing/routing.py:native_search_allowed` makes `run_search` skip LinkedIn native keyword search for them (short company names match worldwide homonyms and burn the read cap; kill-switch `EKOALU_ABM_NATIVE_SEARCH=1`). Global persona campaigns (métallier, maçon…) keep native search. **SECTOR campaigns (01/07)**: a third campaign type sourced via Serper by *sector + role* instead of by company — for personas that map to an activity sector, not a named firm (first case: `EKOALU - SECTEUR - Bailleurs sociaux RA`, for the porte-grand-passage / halls angle). `queries.py:SECTOR_SPECS` is a registry keyed by the slug parsed from `EKOALU - SECTEUR - <slug>` (sector anchor + role terms + geo-bias regions); `build_sector_queries` emits `site:linkedin.com/in "<anchor>" "<role>" <region>` (validated live: anchor `"logement social"` beats `"bailleur social"`, appending `Lyon` biases toward Rhône-Alpes). `queries.build_queries` dispatches ABM vs SECTOR; `routing.is_sector_campaign` makes SECTOR Serper-only too (native search off). Both `source_via_google` and `source_via_google_rotate` select `" ABM - " OR " SECTEUR - "`. Keep `roles × regions ≤ --per-campaign-queries` (9). **Daily rotation**: `manage.py source_via_google_rotate` (scheduled task `EKOALU-Serper-Rotation`, 7:00 Mon-Fri via `scripts/serper_rotation.ps1`) serves ABM + SECTOR campaigns least-recently-served first, stops at `--new-leads-target` (30) or `--max-queries` (60 credits). **Dedup against the base (07/07)**: only profiles UNKNOWN to the base (no existing Lead) count toward the per-campaign quota `max_profiles` — Google reserves the same top-10 every day, so known profiles are re-attached to the campaign (LeadDiscovery) at zero quota cost and the remaining role-queries keep running; when a full page is majority-known, the next Google page is fetched (1 credit/page, cap `EKOALU_SERPER_MAX_PAGES`, default 3 — pagination lives in `service.py`, `client.search_linkedin_results` fetches exactly ONE page per call). **Exhaustion**: a campaign with 2 consecutive COMPLETE runs (all role-queries executed, `SourcingResult.all_queries_run`) yielding zero NEW profiles is flagged exhausted (`GoogleSourcingState`, ekoalu migration 0020) and leaves the rotation; a partial run (query budget spent before the end) never counts. `--reset-exhausted` re-arms, and `serper_rotation.ps1` runs it automatically on the first working day of each month (day ≤ 3, Mon-Fri). Shared per-campaign logic in `ekoalu/google_sourcing/service.py`. **URL-only embed priority (07/07)**: `linkedin/pipeline/qualify.py:fetch_qualification_candidates` embeds up to N URL-only leads of the campaign per cycle (env `EKOALU_URLONLY_EMBED_PER_CYCLE`, default 2) BEFORE serving the embedded pool — one LinkedIn read each, deliberate: the read budget goes to Serper-sourced leads (before, a URL-only lead was only embedded when the pool was empty, which never happened). **Sidebar harvest OFF (07/07)**: `visit_profile` no longer harvests the "people also viewed" profiles visible on a profile page (was up to 10 Voyager reads per visit ≈ 70% of the daily read cap, junk leads attributed to the current campaign with empty query) — kill-switch `EKOALU_SIDEBAR_HARVEST=1` to re-enable; `search_people` (native search RESULTS pages, deliberate persona sourcing) still harvests. **Serper pre-filter (15/06)**: `ekoalu/google_sourcing/prefilter.py:passes_prefilter` écarte un résultat AVANT la lecture LinkedIn si son title/snippet révèle un métier franchement hors-domaine bâtiment (avocat, photographe, postdoc, formateur, data engineer, géomètre…) — économise la lecture des homonymes/hors-cible évidents que Serper ramène malgré la requête `"Company" "role"`. Conservateur (n'exclut QUE l'évident, le tri fin reste au LLM) ; `client.search_linkedin_results` garde title/snippet, `SourcingResult.prefiltered` compte les écartés. Kill-switch `EKOALU_SERPER_PREFILTER=0`. **Pause campagne (15/06)**: `Campaign.active` (linkedin migration 0008) — `active=False` (ex. VIP, dont la recherche native globale ramassait ~38 profils lyonnais hors-cible/jour = 75% du budget lectures gâché) sort la campagne de `AccountSession.campaigns` (filtre `active=True`) : plus de seed connect, plus de qualifier, et le daemon draine ses tasks résiduelles sans les exécuter.
- **Anti-detection browser layer (EKOALU, refonte 11/06)**: real **Chrome** (`channel="chrome"`) via **Patchright** (NOT stock Playwright — fixes the CDP `Runtime.enable` leak + `navigator.webdriver`) in **`launch_persistent_context`** on `data/linkedin_profile/` (persistent cookies/localStorage/IndexedDB/fingerprint = stable trusted device). No `playwright-stealth` (counter-productive). First login is **manual** (`manage.py linkedin_manual_login` → Richard ticks "stay logged in" → `li_rm` device-trust cookie, 1yr); the daemon then reuses the profile and **never auto-logs-in with a password** (`reauthenticate()`/`_maybe_refresh_cookies()` are no-ops). Root cause of the per-login checkpoint: cookies injected into a fresh context = stolen-session signature. `is_authenticated()` dismisses two recurring overlays on the feed: `dismiss_comply_gate` ("Agree to comply" interstitial) and `dismiss_cookie_consent` (cookie privacy banner — clicks "Accept"; it reappeared every session because nothing clicked it, so the consent cookie was never persisted in the profile — 16/06). Full operating mode in `docs/MODE_OPERATOIRE_LINKEDIN.md`; source benchmark in `docs/ANNUAIRE_SOURCES_ANTI_DETECTION.md`.
- **Anti-ban guards (EKOALU)**: layered kill-switches checked by the daemon loop, all in `ekoalu/`. (1) `emergency_stop.py` — manual STOP sentinel `data/emergency_stop.flag`, never auto-purges. (2) `read_guard/` — **hard cap on LinkedIn profile reads/day** (`EKOALU_DAILY_PROFILE_READS_CAP`, default 40; prod **60** since 12/06, auto-ramps to **75 on 2026-06-15** via `EKOALU_PROFILE_READS_CAP_RAMP="YYYY-MM-DD:cap,..."`): patches `PlaywrightLinkedinAPI.get_profile`/`get_connection_degree` (count + raise `ReadCapExceededError` at cap), `ProfileReadDay` DB counter, daemon pauses tasks but keeps draining approved sends; reads were what triggered the 06/06 checkpoint, not sends. (2c) **intra-day read pacing** (anti-burst matinal, remarque Richard 15/06) — `read_guard/guard.py:reads_budget_now()` débloque le cap journalier LINÉAIREMENT sur la plage active (07h-20h) au lieu de tout au réveil ; le daemon temporise ~10min (jitter) quand `is_paced_cap_reached()` est vrai → les lectures s'étalent en filet au lieu de partir en rafale à l'ouverture (75 vues en 1h = signature bot, et cap cramé à 09h qui affamait les relances). Plafond MOU (gating daemon, jamais de raise), distinct du cap dur. Kill-switch `EKOALU_READ_PACING=0` ; plancher `PACING_MIN_FLOOR=5`. (2b) **daily send caps** in `ekoalu/outbound_validation/sender.py:process_approved_queue` — invitations (`EKOALU_DAILY_INVITE_CAP`, 12/d prod) AND LinkedIn messages follow-up+reply (`EKOALU_DAILY_MESSAGE_CAP`, default 15/d, 2026 free-account safe zone 15-20/d); blocked kinds wait for the next day, other kinds keep flowing. (3) `auth_watch.py` — **auto-STOP after N consecutive auth failures** (`EKOALU_AUTH_FAILURES_BEFORE_STOP`, default **1** = stop on first: insisting hardens the checkpoint): engages emergency_stop + mails Richard + leaves the browser window open for manual login. Counter resets on task success. (4) `llm_usage/budget_guard.py` — daily Claude budget ($4). (5) `llm_usage/api_limit_guard.py` — Anthropic org cap.
- **CRM integrity (EKOALU)**: `ekoalu/crm_integrity.py` + `manage.py check_crm_integrity [--fix]` — detects/repairs disqualified-lead-with-active-Deal, open PendingOutbound on dead leads/done deals, duplicate open POs; multi-active-deals reported (fix via `consolidate_duplicate_deals`). `manage.py triage_failed_outbound [--dry-run]` — one-shot triage of FAILED POs (reject obsolete, re-pend transients). Anomaly count + profile-reads counter surfaced in `daily_recap`.
- **Email canal extras (EKOALU)**: `ekoalu/email_canal/bounce.py` — NDR/bounce detection in the inbox poller (postmaster/mailer-daemon senders or NDR subjects), marks `Lead.email_bounced_at`, excluded from sends by `sender._resolve_recipient`. Brique K: `PendingReply.cold_variant` copies the `prompt_variant` of the last sent cold mail for that lead (A/B reply-rate table in `daily_recap`). **Cold-mail idempotence (16/06)**: `generate_cold_emails` skips a lead if it is `disqualified` (a Richard reject = permanent exclusion via `lead_exclusion`) OR already has a cold mail in any of PENDING/APPROVED/SENT/BLOCKED_COMPANY/**REJECTED** — without these two guards a rejected prospect was regenerated every day and resurfaced in the validation queue.
- **Field encryption (EKOALU, Lot 2 RGPD 18/06)**: `ekoalu/crypto.py:EncryptedCharField` — transparent at-rest Fernet encryption (AES-128+HMAC). Key in env `EKOALU_FIELD_ENCRYPTION_KEY` (NEVER in DB; lives in `.env.production`). `SiteConfig.llm_api_key` uses it (ciphertext is `fernet:`-prefixed; legacy plaintext is read as-is and encrypted on next save — see migration `linkedin/0009_encrypt_secrets`). Degrades to plaintext (with a warning) if the key is absent, so the app never fails to boot. `LinkedInProfile.linkedin_password` is no longer stored (blanked) — manual login since 11/06 means no password is ever needed.
- **Config**: `SiteConfig` DB singleton (LLM_PROVIDER, LLM_API_KEY — chiffré at-rest, AI_MODEL, LLM_API_BASE — editable via Django Admin; `llm_provider` chooses between OpenAI/Anthropic/Google/Groq/Mistral/Cohere/openai_compatible, `llm_api_base` only consulted when provider is `openai_compatible`), `conf.py:CAMPAIGN_CONFIG` (timing/ML defaults), `conf.py` browser constants (`BROWSER_*`, `HUMAN_TYPE_*`), `conf.py` schedule constants (`ENABLE_ACTIVE_HOURS` flag, active hours/timezone/rest days), `conf.py` onboarding defaults (`DEFAULT_*_LIMIT`), `conf.py:FASTEMBED_CACHE_DIR` (persistent model cache, defaults to `<project>/.cache/fastembed/`), Campaign/LinkedInProfile models (Django Admin). `VOYAGER_REQUEST_TIMEOUT_MS` lives in `api/client.py` (constructor default on `PlaywrightLinkedinAPI`). `conf.py:DUMP_PAGES` (default `False`) — enable to save page HTML snapshots for fixture collection.
- **Lazy accessors**: `Lead.get_profile(session)` serves the stored `profile_snapshot` (JSON, crm 0015) when present and < 30 days old, else scrapes Voyager once and stores it (`refresh=True` forces a re-scrape). **1 lead = 1 LinkedIn read max** — LLM verdicts, follow-up summaries and message generation read from DB and keep working after the daily read cap (EKOALU 12/06; previously every call was a live scrape and a Serper lead cost 2 reads). `create_enriched_lead` stores the snapshot from the in-hand profile dict. `Lead.get_urn(session)` reads the `urn` column and falls back to a scrape; `Lead.get_embedding(session)` lazily scrapes + embeds on first access, then caches the 384-dim bytes on the row. `Lead.embed_from_profile(profile)` reuses an in-hand profile dict to skip the scrape (used by `create_enriched_lead`). `Lead.to_profile_dict()` returns a minimal `{lead_id, public_identifier, url, meta}` dict (no `profile` key). `AccountSession.campaigns` (cached_property, list). `AccountSession.self_profile` (cached_property, re-discovers via Voyager on first access per session — no DB cache).
- **Deal summaries**: `Deal.profile_summary` and `Deal.chat_summary` are lazy, mem0-style JSON fact lists built on demand and updated incrementally. `linkedin/db/summaries.py` is the single boundary — `materialize_profile_summary_if_missing(deal, session)` fires on the first follow-up touch (one Voyager re-scrape per `(lead, campaign)` lifetime), `update_chat_summary(deal, new_messages)` folds newly-synced ChatMessages into the summary via `reconcile_facts`, which routes new facts through mem0's UPDATE prompt to apply ADD/UPDATE/DELETE/NONE events (no naive append-and-dedup). **Only incoming (lead) messages reach fact extraction** — outgoing seller messages are filtered at the boundary so `chat_summary` stores facts about the lead, never the seller's pitch. A one-sided burst of outgoing messages short-circuits the LLM call entirely. The follow-up agent consumes `profile_summary + chat_summary + last 6 ChatMessage rows` instead of flat profile fields. The fact-extraction prompt is vendored at `linkedin/db/summaries.py:_FACT_EXTRACTION_PROMPT`; mem0's `DEFAULT_UPDATE_MEMORY_PROMPT` and `get_update_memory_messages` are vendored under `linkedin/vendor/mem0/configs/prompts.py` (mirroring upstream paths so future syncs are a clean diff). No `mem0ai` runtime dependency — avoids qdrant/grpcio/sqlalchemy transitive bloat.

# CLAUDE.md

## Rules

- **Python env**: Always use `.venv/bin/python` (not system `python3`).
- **Commits**: No `Co-Authored-By` lines. Single-line messages (no body).
- **Dependencies**: Managed in `requirements/*.txt` (used by local dev and Docker).
- **Docs sync**: When modifying code, update CLAUDE.md and ARCHITECTURE.md to reflect changes.
- **No memory**: Never use the auto-memory system (no MEMORY.md, no memory files). All persistent context belongs in CLAUDE.md or ARCHITECTURE.md.
- **Error handling**: App should crash on unexpected errors. `try/except` only for expected, recoverable errors. Custom exceptions in `exceptions.py`.
- **No API backward compat**: Project has no external users yet — don't preserve old Python APIs, function signatures, or import paths. Rename, delete, and rewrite freely; no shims or re-export modules. DB schema changes still go through Django migrations as normal — existing installs must upgrade cleanly.

## Project Overview

OpenOutreach — self-hosted LinkedIn automation for B2B lead generation. Playwright + stealth for browser automation, LinkedIn Voyager API for profile data, Django + Django Admin for CRM (models owned by this project).

## Architecture (quick reference)

For detailed module docs, see `ARCHITECTURE.md`.

- **Entry**: `manage.py` — stock Django management. `rundaemon` command (migrate → onboard → validate → task queue loop). `manage.py` with no args defaults to `rundaemon`. Onboarding logic in `onboarding.py`: `OnboardConfig` (pure dataclass), `missing_keys()`, `collect_from_wizard()`, single `apply()` write path. Docker `start` script handles Xvfb/VNC, then `exec python manage.py rundaemon`.
- **State machine**: `enums.py:ProfileState` — QUALIFIED → READY_TO_CONNECT → PENDING → CONNECTED → COMPLETED / FAILED. `Deal.connected_at` (crm 0014) stamps the first PENDING→CONNECTED transition (set in `linkedin/db/deals.py:set_profile_state`) — feeds the dashboard "invitations acceptées/jour" chart. Deal.state is a CharField with ProfileState choices (no Stage model). `Outcome` (converted/not_interested/wrong_fit/no_budget/has_solution/bad_timing/unresponsive/unknown) on Deal.outcome. `Lead.disqualified=True` = permanent exclusion. LLM rejections = FAILED Deals with wrong_fit outcome (campaign-scoped).
- **Task queue**: `Task` model (persistent). Three types: `connect`, `check_pending`, `follow_up`. Handlers in `linkedin/tasks/`, signature: `handle_*(task, session, qualifiers)`. Task creation is centralized in `linkedin/tasks/scheduler.py` — no other module inserts Task rows. `set_profile_state()` fires `on_deal_state_entered(deal)`, which enqueues the task implied by the new state (CONNECTED → follow_up, PENDING → check_pending). **Connect quota (15/07)**: `claim_next()` serves a DUE connect FIRST while fewer than `EKOALU_DAILY_CONNECT_QUOTA` (default 12) connect tasks have completed today — without this floor, the LOT C type priority starved connects entirely (0 served 08-13/07; qualification runs INSIDE handle_connect, so 0 deals and 0 invitations followed). The quota never applies to a restricted claim (`task_types=`, the read-pacing follow_up pass-through). **Type priority (LOT C 07/07)**: past the quota, `Task.objects.claim_next()` serves, among DUE tasks, follow_up first, then check_pending, then connect (FIFO on `scheduled_at` within a type; `task_types=` restricts the claim) — a permanent connect backlog no longer starves the follow-ups. **Pending-validation recheck backoff (15/07)**: when a follow_up finds (or creates) a PendingOutbound awaiting Richard's validation, the recheck task is re-enqueued in 8-12h jittered (was 4h — ~23 waiting relances cycling at 4h monopolized the daemon's action slots); the actual send is driven by the approved queue, not by this recheck. **Reconcile (LOT C)**: `reconcile(session)` runs at daemon startup, then at most every `RECONCILE_INTERVAL_SECONDS` (30 min) even when the queue never drains, plus the historic "no ready task" trigger. It recovers stale RUNNING rows, seeds one connect per campaign, and re-creates tasks for any active Deal without a pending task (PENDING → check_pending, CONNECTED → follow_up). This is the retry mechanism — a crashed handler leaves a FAILED task with no successor, and the next reconcile re-creates it (cap: `MAX_FAILED_RETRIES=2` per payload per 24h). On 401 (`AuthenticationError`), the daemon marks the task FAILED (no auto re-login); reconcile picks it up. **Résilience LLM (fiche #36, 02/09)** : `ModelHTTPError` n'arrête plus le daemon sauf 401/403 (config morte) ; 429/5xx = backoff 120s ; 400 et autres = task FAILED + la boucle CONTINUE (les étages sans LLM — connects, drain, check_pending — restent actifs ; la panne « temperature » du 25/08 avait arrêté le daemon 47 fois pendant 6 jours). Compteur `llm_error_streak` : tous les 5 échecs consécutifs, événement `severity=error` au hub (`daemon.py:llm_error_action`). Logs forcés en UTF-8 (`linkedin/logging.py:force_utf8` + `PYTHONIOENCODING` dans start_daemon.bat) — avant, toute ligne avec → ou ▶ devenait « --- Logging error --- » en cp1252, y compris le message d'alerte lui-même.
- **Interception vs échec (LOT C 07/07)**: in `require_approval` mode, the patched `send_connection_request`/`send_raw_message` return the falsy sentinel `linkedin.enums.INTERCEPTED` when the invitation/message is captured as a PendingOutbound (creation AND ABM dedup). Handlers test identity: `handle_follow_up` keeps the Deal **CONNECTED** and re-checks in 8-12h (15/07 backoff; was 4h) (before: the `False` return was read as a send failure → CONNECTED demoted to QUALIFIED, every generated relance broke its own chain); `handle_connect` counts **no** connect attempt (before: 3 waiting-for-Richard cycles = wrongful "Unreachable" disqualification). A real send failure (plain `False`) keeps the old failure behavior.
- **ML pipeline**: GPR (sklearn) + BALD active learning + LLM qualification. Per-campaign models stored in `Campaign.model_blob` (DB). **EKOALU lead routing** (`ekoalu/lead_routing/`, patches `create_enriched_lead` + `get_leads_for_qualification` via `apps.py`): each Lead is attributed to the campaign that discovered it (`LeadDiscovery` model), and a campaign only qualifies *its own* discovered leads instead of the whole base — kills the cross-campaign over-qualification (~97% wrong_fit by construction). Kill-switch `EKOALU_SCOPED_QUALIFICATION=0` or sentinel `data/scoped_qualification_disabled.flag`. Backfill in-flight leads with `manage.py backfill_lead_sources`. Per-campaign targeting criteria (geo + role rules) live in `Campaign.campaign_objective`, applied from the ops Excel via `manage.py apply_campaign_criteria`. **Google sourcing** (`ekoalu/google_sourcing/`, command `manage.py source_via_google`): finds LinkedIn profile URLs via Google search results (`site:linkedin.com/in "Company" "role"`) instead of LinkedIn's own search, creates URL-only leads + `LeadDiscovery` (the daemon enriches/qualifies them later in its own browser session — no second browser). Backend: **Serper.dev** (Google Custom Search JSON API is closed to new customers since 2026). Config: env `SERPER_API_KEY` (1 credit/query, 2,500 free trial credits). ABM-first. **Source routing (12/06)**: ABM campaigns are sourced via Serper ONLY — `ekoalu/google_sourcing/routing.py:native_search_allowed` makes `run_search` skip LinkedIn native keyword search for them (short company names match worldwide homonyms and burn the read cap; kill-switch `EKOALU_ABM_NATIVE_SEARCH=1`). Global persona campaigns (métallier, maçon…) keep native search. **SECTOR campaigns (01/07)**: a third campaign type sourced via Serper by *sector + role* instead of by company — for personas that map to an activity sector, not a named firm (first case: `EKOALU - SECTEUR - Bailleurs sociaux RA`, for the porte-grand-passage / halls angle). `queries.py:SECTOR_SPECS` is a registry keyed by the slug parsed from `EKOALU - SECTEUR - <slug>` (sector anchor + role terms + geo-bias regions); `build_sector_queries` emits `site:linkedin.com/in "<anchor>" "<role>" <region>` (validated live: anchor `"logement social"` beats `"bailleur social"`, appending `Lyon` biases toward Rhône-Alpes). `queries.build_queries` dispatches ABM vs SECTOR; `routing.is_sector_campaign` makes SECTOR Serper-only too (native search off). Both `source_via_google` and `source_via_google_rotate` select `" ABM - " OR " SECTEUR - "`. Keep `roles × regions ≤ --per-campaign-queries` (9). **Daily rotation**: `manage.py source_via_google_rotate` (scheduled task `EKOALU-Serper-Rotation`, 7:00 Mon-Fri via `scripts/serper_rotation.ps1`) serves ABM + SECTOR campaigns least-recently-served first, stops at `--new-leads-target` (30) or `--max-queries` (60 credits). **Dedup against the base (07/07)**: only profiles UNKNOWN to the base (no existing Lead) count toward the per-campaign quota `max_profiles` — Google reserves the same top-10 every day, so known profiles are re-attached to the campaign (LeadDiscovery) at zero quota cost and the remaining role-queries keep running; when a full page is majority-known, the next Google page is fetched (1 credit/page, cap `EKOALU_SERPER_MAX_PAGES`, default 3 — pagination lives in `service.py`, `client.search_linkedin_results` fetches exactly ONE page per call). **Exhaustion**: a campaign with 2 consecutive COMPLETE runs (all role-queries executed, `SourcingResult.all_queries_run`) yielding zero NEW profiles is flagged exhausted (`GoogleSourcingState`, ekoalu migration 0020) and leaves the rotation; a partial run (query budget spent before the end) never counts. `--reset-exhausted` re-arms, and `serper_rotation.ps1` runs it automatically on the first working day of each month (day ≤ 3, Mon-Fri). Shared per-campaign logic in `ekoalu/google_sourcing/service.py`. **URL-only embed priority (07/07)**: `linkedin/pipeline/qualify.py:fetch_qualification_candidates` embeds up to N URL-only leads of the campaign per cycle (env `EKOALU_URLONLY_EMBED_PER_CYCLE`, default 2) BEFORE serving the embedded pool (before, a URL-only lead was only embedded when the pool was empty, which never happened). **Apify-first (07/07)**: when Apify is ready (token + kill-switch + daily cap), each of these embeds is a cookieless Apify fetch — zero Voyager read, read_guard cap untouched; Voyager fallback (one account read, LOT C pacing) on Apify failure or when unconfigured. **Sidebar harvest OFF (07/07)**: `visit_profile` no longer harvests the "people also viewed" profiles visible on a profile page (was up to 10 Voyager reads per visit ≈ 70% of the daily read cap, junk leads attributed to the current campaign with empty query) — kill-switch `EKOALU_SIDEBAR_HARVEST=1` to re-enable; `search_people` (native search RESULTS pages, deliberate persona sourcing) still harvests. **Serper pre-filter (15/06)**: `ekoalu/google_sourcing/prefilter.py:passes_prefilter` écarte un résultat AVANT la lecture LinkedIn si son title/snippet révèle un métier franchement hors-domaine bâtiment (avocat, photographe, postdoc, formateur, data engineer, géomètre…) — économise la lecture des homonymes/hors-cible évidents que Serper ramène malgré la requête `"Company" "role"`. Conservateur (n'exclut QUE l'évident, le tri fin reste au LLM) ; `client.search_linkedin_results` garde title/snippet, `SourcingResult.prefiltered` compte les écartés. Kill-switch `EKOALU_SERPER_PREFILTER=0`. **Pause campagne (15/06)**: `Campaign.active` (linkedin migration 0008) — `active=False` (ex. VIP, dont la recherche native globale ramassait ~38 profils lyonnais hors-cible/jour = 75% du budget lectures gâché) sort la campagne de `AccountSession.campaigns` (filtre `active=True`) : plus de seed connect, plus de qualifier, et le daemon draine ses tasks résiduelles sans les exécuter.
